# شهر دیجیتال — بازی چندنفره‌ی آنلاین

یک شهر سه‌بعدیِ مشترک (Three.js) که همه‌ی بازیکن‌های آنلاین هم‌زمان داخلش هستن.
هر آدمی که توی شهر می‌بینی یک **بازیکن واقعیِ لاگین‌کرده**ست — هیچ NPC انسانی وجود نداره.
اگه هیچ‌کس دیگه آنلاین نباشه، شهر خالی از آدمه (رفتار درست، نه باگ). ماشین‌ها و موانع می‌مونن.

- **اکانت:** ثبت‌نام/ورود با نام کاربری و رمز (هش bcrypt، ۱۲ راند)، نشست با JWT داخل کوکی httpOnly
- **امتیاز روی هوا:** با دویدن، پریدن از مانع و مأموریت‌ها جمع می‌شه — همه‌ش رو سرور حساب می‌کنه
- **گلوبانک:** جلوی هر شعبه امتیاز روی هوا به فیت‌کوینِ امن تبدیل می‌شه (در دیتابیس سرور)
- **PvP:** ۳ مشت یا ۲ لگد. برنده تمام امتیازِ بانک‌نشده‌ی بازنده رو می‌گیره؛ فیت‌کوین بانکی دست‌نخورده می‌مونه
- **مغازه‌ی بازیکن:** با ۳۰۰ فیت‌کوین بانکی یک مغازه‌ی واقعی در یک جای یکتای شهر؛ محصول با عکس، قیمت و لینک پرداخت
- فروشگاه‌های ثابت (دیجی‌کالا، خانومی، علی‌بابا، اسنپ‌فود، بلوبانک)، فروشگاه لباس، جدول رتبه‌ها

> بازی خودش پرداخت انجام نمی‌ده؛ دکمه‌ی «خرید» فقط خریدار رو به لینک پرداختی که فروشنده گذاشته می‌بره.

## اجرا

```bash
cd digital-city
npm install
npm start            # http://localhost:3000
npm test             # تست سرتاسری سرور (دو بازیکن واقعی با سوکت)
```

نیاز: Node.js 20 یا بالاتر.

| متغیر محیطی | توضیح |
|---|---|
| `PORT` | پورت (پیش‌فرض 3000) |
| `DB_PATH` | مسیر فایل SQLite (پیش‌فرض `data/city.db`) |
| `JWT_SECRET` | کلید امضای نشست. در production حتماً ست کنید. اگر نباشد یک کلید تصادفی در `data/.jwt-secret` ساخته می‌شود |
| `NODE_ENV=production` | کوکی‌ها `Secure` می‌شوند (نیاز به HTTPS) |
| `TRUST_PROXY=1` | وقتی پشت پروکسیِ هاست (Render/Railway/Fly) هستید، تا rate limit آی‌پی واقعی را ببیند |

## ⚠️ هاستینگ: دیگر یک فایل HTML نیست

نسخه‌ی قبلی یک فایل HTML بود که آفلاین باز می‌شد. این نسخه **یک سرور Node.js دائمی** لازم دارد
(برای WebSocket و دیتابیس). گزینه‌ها: Render، Railway، Fly.io یا هر VPS.

- فولدر `data/` (یا مسیر `DB_PATH`) باید روی **دیسک ماندگار** باشد، وگرنه با هر دیپلوی اکانت‌ها پاک می‌شوند
  (در Render/Railway یک Volume/Disk وصل کنید).
- HTTPS + `NODE_ENV=production` + یک `JWT_SECRET` طولانی و تصادفی.
- این نسخه برای **یک پروسه‌ی سرور** نوشته شده (وضعیت زنده‌ی بازیکن‌ها در حافظه است). برای چند instance
  باید Socket.io Redis adapter و انتقال state به Redis اضافه شود.

## ساختار

```
shared/world.js     قوانین مشترک سرور و کلاینت: شبکه‌ی شهر، بانک‌ها، موانع، ترافیک، لباس‌ها، اعداد مبارزه
server/index.js     Express + Socket.io، هدرهای امنیتی (CSP و...)
server/game.js      دنیای زنده: حضور، اعتبارسنجی حرکت، مبارزه، کشتن/غارت، ری‌اسپان، امتیاز، مأموریت، واریز
server/routes.js    REST API: اکانت، بانک، لباس، مغازه و محصولات، عکس‌ها
server/security.js  JWT، rate limit، اعتبارسنجی ورودی و عکس
server/db.js        SQLite (better-sqlite3) + migrationها — تمام SQL فقط در همین فایل
public/             صفحه‌ی ورود (index.html) و بازی (game.html)
  js/game.js        حلقه‌ی بازی، کنترل‌ها، شبکه، نمایش بقیه‌ی بازیکن‌ها با interpolation
  js/city.js        رندر شهر بی‌نهایت، مغازه‌ها، موانع، ماشین‌ها، برخورد
  js/character.js   مدل آدمک (buildCharacter) برای همه‌ی بازیکن‌ها
  js/ui.js          پنل‌ها: مغازه‌ی من، محصولات، بازدید مغازه، لباس، رتبه‌ها
test/server.test.js تست سرتاسری
```

## مدل داده

`users` (bank_fitcoin، current_score، لباس‌ها، سلامتی، آخرین موقعیت، kills/deaths)،
`shops` (یک مغازه برای هر کاربر، `UNIQUE(block_i, block_j, lot)` تا دو مغازه روی هم نیفتند)،
`products`، `kill_log` (هر کشتن و مقدار منتقل‌شده — برای شفافیت و بررسی تقلب).

**چرا ORM نه؟** Prisma موقع نصب موتورهای باینری دانلود می‌کند و راه‌اندازی را سخت‌تر می‌کرد.
به جایش همه‌ی SQL ساده و استاندارد در `server/db.js` جمع شده و migrationها با `PRAGMA user_version`
اجرا می‌شوند. برای مهاجرت به Postgres فقط همین یک فایل باید با `pg` بازنویسی شود
(`INTEGER PRIMARY KEY AUTOINCREMENT` → `SERIAL`، `COLLATE NOCASE` → `CITEXT` یا ایندکس روی `lower(username)`).

## امنیت و ضدتقلب

- سرور منبع حقیقت است: امتیاز، سلامتی، ضربه، کشتن، واریز و خریدها همه سمت سرور اعتبارسنجی می‌شوند.
  کلاینت فقط «حرکت کردم / مشت زدم / از مانع X پریدم» می‌فرستد.
- حرکت: سرعت غیرممکن رد و بازیکن به موقعیت سرور برگردانده می‌شود؛ «معلق ماندن در هوا» بیش از ۱.۵ ثانیه پذیرفته نمی‌شود.
- مبارزه: فاصله، جهت نگاه، کول‌داون، زنده بودن، مصونیت و منطقه‌ی امن روی سرور چک می‌شود.
- واریز: فقط وقتی سرور شما را جلوی یک شعبه ببیند. پرش از مانع: فقط نزدیک همان مانع.
- rate limit: ورود (۳۰ تلاش در ۱۰ دقیقه برای هر IP، قفل ۱۰ دقیقه‌ای نام کاربری بعد از ۸ رمز اشتباه)،
  ثبت‌نام (۱۰ در ساعت برای هر IP)، نوشتن‌های API (۶۰ در دقیقه)، پیام‌های سوکت (۶۰ در ثانیه، بیشتر = قطع).
- XSS: هیچ متن کاربری با innerHTML رندر نمی‌شود (فقط textContent و canvas)؛ CSP سخت‌گیر (`script-src 'self'`)؛
  کاراکترهای کنترلی و جهت‌دهی (bidi override) از اسم‌ها حذف می‌شوند.
- عکس‌ها: سمت کلاینت به ۲۵۶ پیکسل و JPEG فشرده می‌شوند؛ سرور فقط JPEG/PNG/WebP با magic bytes درست و
  حداکثر ۳۰۰KB می‌پذیرد و با Content-Type درست و `nosniff` سرو می‌کند.
- لینک پرداخت فقط `http/https` (نه `javascript:`)؛ در پنل دامنه‌ی مقصد به خریدار نشان داده می‌شود.
- CSRF: درخواست‌های تغییردهنده فقط با `Content-Type: application/json` و کوکی `SameSite=Lax`.
- یک اکانت فقط در یک تب: ورود دوباره، تب قبلی را بیرون می‌کند.

## کنترل‌ها

جوی‌استیک یا `WASD`/جهت‌ها · پرش: دکمه یا `Space` · مشت: `J` · لگد: `K` · ورود به مغازه / واریز: `E`
(یا مشت زدن جلوی در مغازه).

## چیزهایی که برای بعد مانده

- Area of interest: الان هر snapshot برای همه‌ی بازیکن‌ها فرستاده می‌شود؛ برای صدها نفر هم‌زمان باید فقط بازیکن‌های نزدیک فرستاده شوند.
- چند instance سرور (Redis adapter).
- ذخیره‌ی عکس‌ها روی object storage به‌جای دیتابیس اگر تعداد محصولات خیلی زیاد شد.
